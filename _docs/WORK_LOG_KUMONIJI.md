- `server/kumoniji/multi/ws.py` `/api/ws`: 웹은 Origin + 쿠키, 앱은 첫 메시지 `auth` 토큰. 계정당 연결 1개(새 연결이 옛 연결을 4409로 닫고, 대기열·판 자리는 유지), 2KB(1009)·초당 10개(1008)·유휴 60초(4408), 60초마다 세션 재확인(로그아웃 → 4401). 다시 붙으면 현재 판 상태. 끊기면 대기열·방에서 빠지고 판에서는 끊김 표시. 타이머는 api lifespan의 `tick_forever`(0.5초)가 돌린다.
- `accounts/web.py`: `session_problem`(세션·MFA·인증 검사)을 HTTP·소켓이 같이 쓰게 분리, `socket_session`.
- 막힌 점: 소켓 테스트가 끝난 뒤 멈춤 → 원인은 테스트가 연 소켓을 닫지 않아 서버 쪽 처리가 남아 TestClient 종료가 기다린 것. ExitStack으로 닫음. 한 판 테스트는 초당 제한(1008)에 걸려 그 테스트만 제한을 올림.
- Codex 지적으로 고침: ① 운영 이미지에 `websockets`가 없어 uvicorn이 업그레이드를 404로 거부 — **실제 uvicorn으로 재현**(TestClient는 uvicorn을 안 거쳐 못 잡음) → `websockets==15.0.1` 추가 후 같은 시험에서 4401(인증 거부)·다른 Origin 403 확인. ② 브라우저는 기기 머리글을 못 달아 User-Agent가 기기로 쓰였는데 남남끼리도 같음 → 기기는 앱 머리글만, 없으면 IP만 비교. ③ 막힌 연결에 보내기가 타이머 전체를 붙잡음 → 보내기 2초 제한, 넘기면 그 연결 닫음. ④ 교체된 옛 연결이 이미 받은 메시지를 처리 → 메시지마다 현재 연결인지 확인. ⑤ 대기 중 다시 붙으면 `lobby`로 보냄 → `queued`.
- 2차 지적: 보내기 실패 연결을 목록에서 먼저 빼면 그 연결의 정리(대기열·판 끊김 표시)가 안 돎 → 목록은 두고 '실패한 연결' 표시만. 재접속 둘이 겹치면 중간 연결이 최신을 덮음 → 닫은 뒤 다시 확인. 한 번의 알림에 다른 시점 상태가 섞임 → 네 자리 상태를 먼저 만들고 보냄. 매칭이 앞사람부터 욕심내 가능한 4명을 놓침(1번이 2번과 IP, 3번과 기기 공유) → 새 사람 + 먼저 온 셋 조합을 오래 기다린 순으로(앞 50명).
- 3차 지적(보내기 순서 역전·타이머가 느린 연결을 기다림)은 같은 뿌리 — 보내기를 하나씩 기다린 설계. 연결마다 보낼 줄 + 전용 작업으로 바꿈(send는 넣기만, 64개 쌓이면 닫음). 그 밖에 대기 중 재접속 시 새 IP 반영, 매칭 앞 50명 제한 대신 고를 때마다 후보를 줄이는 탐색(같은 IP 60명 뒤도 찾음), 30분 지난 방 사람에게 `lobby` 알림, 첫 인증 메시지도 2KB 검사.
- 4차 지적: 2KB 검사는 uvicorn이 메시지를 다 받은 뒤라 인증 전 큰 메시지로 메모리를 채울 수 있음 → Dockerfile에 `--ws-max-size 4096`(실제 uvicorn에서 100자 → 4401, 1만 자 → 1009 확인). 재접속으로 IP가 바뀌면 그 자리에서 다시 매칭, 매칭 뒤 남은 대기자에게도 인원 알림.
- 5차 지적: 취소(`unqueue`·`room.leave`)가 매칭·시작 직후에 오면 `lobby`를 보내 판을 놓침 → 지금 처지 하나를 알리는 `_status`(진행 판 > 방 > 대기열 > 끊긴 사이 끝난 판 > 로비)로 통일. 끊긴 사이 끝난 판은 다시 붙으면 결과 상태를 보냄.
- 6차 지적: 60초 재확인이 연결 때 토큰을 다시 검사해 15분 뒤 토큰 만료로 끊김(대기열·방 잃음) → 세션 자체가 살아 있는지(`sessions.live`: 폐기·auth_version·탈퇴·잠금)만 봄. 소켓 인증·재확인 DB 조회는 동시 4개까지(DB 풀 8을 로그인에 남김).
- 7차 지적: 두 IP에 대기자가 몰리면 매칭 탐색이 세제곱(400명 1.1초) → IP마다 앞 4명 후보 + 탐색 상한(12차에서 이분 매칭으로 대체). 소켓 재확인에 30일 유휴 만료도 적용.
- 9차 지적: 인증 안 한 연결 수 상한(전체 100·IP당 5, 넘으면 1013), DB 대기까지 5초 안. 기기 머리글은 클라이언트 값이라 보조일 뿐 — ADR-0023에 한계로 적음.
- 10차 지적: 인증 시간 초과로 취소돼도 스레드의 DB 조회는 계속 돌아 자리가 먼저 풀림 → 스레드가 끝날 때 자리 반납(`_db`).
- 11차 지적: 재확인 DB 조회가 늦으면 수신·정리가 멈춤 → 재확인도 5초 제한, 넘으면 닫음.
- 12차 지적: 탐색 상한에 걸리면 가능한 판도 포기 → 매칭을 이분 그래프 매칭(사람 = IP—기기 선, 크기 3)으로 바꿔 증가 경로로 찾음 — 있으면 반드시 찾고 대기열 길이에 비례(같은 기기 200명 앞에서도 0.05초 안). 앞의 'IP마다 4명'·상한은 지움. 인증 대기 상한 초과는 수락 후 1013으로 바꿨다가 26차 지적(한도 밖 소켓이 쌓임)으로 업그레이드 전 거절(uvicorn 403)로 되돌림 — 막는 쪽을 고름.
- 13차 지적: 대기열에 없는 사람의 `unqueue`·끊김도 모든 대기자에게 인원을 다시 보냄(느린 대기자가 64개 한도로 끊길 수 있음) → 실제로 빠졌을 때만 알림.
- 14차 지적: 바이너리 프레임이 KeyError로 루프를 깨뜨림 → 1003으로 닫음.
- 15차 지적: 웹(기기 모름)의 대체 키 "#계정"이 앱 기기 값과 겹칠 수 있음 → 종류를 붙인 튜플 키.
- 16차 지적: 재확인이 수신 루프를 멈춰 마감 전 수가 타이머에 밀리고, 쌓인 메시지가 한꺼번에 읽혀 초당 제한에 걸림 → 재확인을 연결마다 따로 도는 작업(`_watch`)으로 분리(11차의 5초 제한도 그쪽으로).
- 17차 지적: 대기 인원 알림이 입퇴장마다 전원에게 쌓임 → 표시만 하고 타이머(0.5초)가 사람당 한 통(같은 인원은 안 보냄), 들어온 사람에게만 바로. 세션 폐기를 알면 닫히기를 기다리지 않고 바로 대기열·방에서 뺌(`_leave` 공용).
- 18차 지적: 방 알림에 받는 사람 자신이 어느 칸인지 없음(닉네임 중복 가능) → `me` 칸 번호.
- 19차 지적: 결과 다시 보내기는 재접속 때만(대기 취소에 옛 결과가 뜨던 것), 깊은 중첩 JSON도 bad_message(3.13에선 재현 안 됨, 버전 대비).
- 20차 지적: 처지 알림(`_status`)이 방 전원에게 방 상태를 다시 보냄 → 본인에게만.
- 21차 지적: 보내기가 밀려 닫는 연결도 닫히기 전까지 대기열·방에 남아 매칭에 낌 → `_drop`이 바로 `_leave`(새 연결에 밀린 옛 연결은 CONNS를 먼저 바꿔 자리 유지).
- 22차 지적: 알림을 보내는 도중 밀린 연결을 정리하면 그 정리의 알림이 끼어들어, 남은 사람이 옛 방 상태(옛 me)를 마지막으로 받음 → 상태는 바로 바꾸고 알림만 다음 차례(`call_soon`), 알림은 보내기 전에 다 만듦. 테스트는 고치기 전 실패·고친 뒤 통과 확인.
- 23차 지적: 유휴·크기·속도·바이너리로 닫을 때도 닫힘 전송을 기다리는 사이 대기열에 남음 → 닫기로 정한 순간 `_leave`.
- 24차 지적: 미룬 알림이 그사이 정리된 방을 다시 보냄 → 보낼 때 아직 있는 판·방인지 확인(고치기 전 실패 확인).
- 25차 지적: 미룬 끊김 알림이 그사이 끝난 판 상태를 방 알림 뒤에 보냄 → 끊김 표시는 진행 중인 판에만(고치기 전 실패 확인).
- 27차 지적: 아무도 못 이기는지 판정(센 5장 바닥이면 0.15초)을 자동 패스마다 세 번 → 한 바퀴에 한 번(패스는 바닥·손패를 안 바꿈). 28차 지적(첫 판정도 루프를 0.1초 붙잡음)으로 판정 자체를 고침: `bots._can_beat5`가 바닥보다 셀 수 있는 종류만(묶음 아무거나·같은 색·같은 모양별 수열, 풀하우스, 포카드) 만들고 처음 찾으면 멈춤 — 최악 145ms → 0.3ms, 무작위 400판에서 전부 만드는 방식과 같은 답(싱글 자동 패스도 같이 빨라짐).
- 29차 지적: 늦게 온 옛 수가 같은 사람의 다음 차례에 적용될 수 있음 → 상태에 수 번호 `ply`, 수 메시지에 필수, 다르면 거부. 재확인 55초(+DB 5초 ≤ 로그아웃 뒤 60초).
- 30차 지적: 재확인 주기를 조회 시작 기준으로(늦은 조회가 다음을 밀지 않게). "직전 상대 다시 만남"은 계획 오독 — 계획 C는 끝나면 다시 누르라는 뜻이고 사람이 적을 때 막으면 판이 안 열림, 주석으로 명시.
- 31차 지적: 증가 경로가 가장 오래 기다린 사람을 뒤에 온 같은 IP 사람으로 바꿔 넣음 → 오래 기다린 순으로 "넣어도 네 명을 채울 수 있나"(이분 매칭)를 보고 넣는 선착순. 작은 대기열 2,000개를 전부 따져 본 답(사전순 최소 조합)과 일치, 500명 무작위 0.05초 안. 인증 실패 연결은 닫힘이 끝날 때까지 "인증 중"으로 셈.
- 32차 지적: 계획 C 프로토콜 절에 ply·me·lobby·닫힘 코드 반영, 재확인의 4401 닫힘은 shield(정리 단계 취소에도 끝까지).
- 33차 지적: 서명이 틀린 토큰도 DB 자리를 씀 → DB 전에 서명 확인(`sessions.decode`). DB 자리를 새 연결 인증 3·재확인 2로 나눠 인증이 몰려도 멀쩡한 연결이 안 끊기게. 전체 테스트가 한 번 1개 실패 후 재현 안 됨 → 시간 측정 테스트 기준을 넉넉히(잡으려는 1.1초·1.5초 지연은 그대로 잡힘).
- 34차 지적: 1시간마다 도는 계정 정리의 DB 작업이 이벤트 루프에서 돌아 멀티 타이머·수신을 멈출 수 있음 → 스레드로. 매칭에서 넣을 수 없는 후보가 몰리면 제곱 시간(2,000명 0.38초) → IP·기기가 같은 묶음은 한 번 "안 됨"이면 다시 안 따짐(2.6ms).
- 35차 지적(6차와 반대): 처음 토큰 만료를 안 보니 탈취한 토큰으로 계속 쓸 수 있음 → 소켓도 토큰 만료 때 4401. 대신 앱은 갱신한 토큰을 `{"t":"auth"}`로 보내 이어 가고(같은 계정·세션만), 웹은 갱신 뒤 재연결(자리 유지). 계획 C 프로토콜에 반영.
- 36차 지적: 만료 뒤 닫히기 전 틈에 온 수도 거부(`auth` 오류).
- 37차 지적: 재확인 조회를 기다리는 사이 토큰이 만료돼도 조회가 끝날 때까지 대기열에 남아 손패를 받을 수 있음 → 조회 대기를 "5초와 만료까지 중 짧은 쪽"으로.
- 38차 지적: 만료로 빠지면 웹이 4401 뒤 재연결해도 자리를 잃음 → 만료 60초 전 `{"t":"renew"}` 안내(앱은 새 토큰을 auth로, 웹은 쿠키 갱신 뒤 재연결 — 둘 다 자리 유지). 끝까지 안 한 연결만 빠지는 건 탈취 토큰 차단을 위한 의도(계획 C 프로토콜에 적음).
- 39차 지적: 이미 안내 구간인 토큰으로 붙으면 안내 없이 만료 → 바로 안내. 재확인 조회 중 갱신해도 조회 시작 때 만료 시각으로 닫던 것 → 0.5초마다 만료 시각을 다시 봄(고치기 전 실패 확인).
- 40차 지적: 인증 DB 조회 중 만료된 토큰은 등록 전에 거절(손패·기존 연결 교체 없음). 포기한 재확인 조회는 취소해 자리를 막지 않게.
- 41차 지적: 감시 작업이 닫기 전 틈에 만료된 대기자가 매칭돼 손패를 받음 → 매칭·시작이 일어날 수 있는 모든 메시지와 재접속 전에 만료된 대기자·방 사람을 먼저 뺌(고치기 전 실패 확인).
- 42차 지적: 정리 중 요청자 자신이 만료돼 빠져도 처리를 이어 대기열에 유령이 남음 → 정리를 수신 루프로 옮기고 빠졌으면 멈춤. 보내기 작업이 만료·대표 해제된 연결에도 쌓인 상태를 보냄 → 보내기 직전 확인 후 4401(고치기 전 실패 확인).
- 43차 지적: 갱신이 만료 시각만 바꾸고 인증 버전은 옛것이라 이메일 변경 뒤 갱신해도 재확인에서 끊김 → 가장 새 토큰의 버전을 따름(고치기 전 실패 확인). 만료 연결엔 오류 알림도 안 보내고 4401로 닫히게 테스트 기대 수정.
- 44차 지적: 재확인 조회 도중 갱신으로 버전이 오르면 옛 버전 실패로 끊김 → 조회는 시작 시점 사본으로, 끝났을 때 버전이 바뀌었으면 새 버전으로 다시 조회(고치기 전 실패 확인).
- 검증: 서버 전체 504 통과(로컬 kumoniji-db로 계정 테스트 포함 — 소켓 14개, 로비 12개). 실제 uvicorn으로 업그레이드 확인.

### 오류·막힌 점
- 기획표대로 만든 중급(센 패 아낌·계획 깨면 패스)이 초급 셋 상대 1등 30%·점수 −70. 가설 셋(13 아낌/패스 과다/옛 봇보다 약함)을 변형으로 비교: 아끼지 않기만 27%, 계획을 깨더라도 냄 52%, 옛 탐욕 봇 63%, 계획 선 + 계획 안 깨는 패 우선·없으면 가장 약한 패 69% → 채택. 원인은 패스 과다(남은 13마다 ×2라 쥐고 버티면 손해).
- 상급: 끝판(20장) 몬테카를로만으로는 1등 28.8%(점수만 목표)·32.1%(1등 가중). 200판 결과(39.5%)는 잡음이었음 — 1,000판으로만 판단. 36장부터 계산 36.0%, 44장 35.3%, 샘플을 늘려도 오르지 않음. **기준 40%는 못 맞춤**(점수 순서는 맞음).
- `pkill -f exp4.py`가 그 명령을 실행하던 셸까지 죽여 같은 명령 안의 상수 추가가 적용되지 않음 → 서로 다른 설정 넷이 소수점까지 같은 결과로 드러남. 호출 수를 세서 확인 후 다시 적용.

- 테스트에서 `SharedPreferences.getInstance()`가 끝나지 않아 첫 판이 시작되지 않음 → 테스트 `setUp`에 `setMockInitialValues({})`.

- 고침: `api.py` 미들웨어로 `/api/` 밖 응답에 `Cache-Control: no-cache`(바뀌지 않으면 304). 이미 Cloudflare에 남은 옛 파일은 퍼지하거나 만료를 기다려야 함.
- 사용자: 자동 패스는 "내 패가 없을 때"가 아니라 "더 높은 조합을 아무도 낼 수 없을 때"여야 한다 — 그렇지 않으면 손패가 드러남. `can_beat(table, 모든 손패)`(= 아직 안 나온 패, 공개 정보)로 바꿈. 싱글·페어·트리플은 같은 숫자 묶음으로 직접, 5장만 `plays`(51장 최악 0.14초 측정). "낼 수 있는 패가 없어요" 안내 복원.
- 테스트: 서버 128 passed(남의 손에 산13이 있으면 자동 패스 안 함 → 산13이 나오면 자동 패스, can_beat 크기별, 웹 no-cache — 변경 전 코드로 no-cache 테스트 실패 확인). 앱 analyze 무이상·12 passed.
