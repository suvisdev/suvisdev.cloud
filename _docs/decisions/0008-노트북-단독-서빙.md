# ADR-0008: 노트북 단독 서빙

상태: 확정 (2026-11-08)

## 문제

2026-10-05부터 노트북이 서빙하고, 노트북이 없으면 집컴이 이어받았다. DB·Redis는 집컴 한 곳에 있었다. 11-08에 집컴 Postgres가 15:35, 15:54, 16:34 세 번 `exit code 2`로 크래시했다. 집컴 WSL 디스크는 HDD이고 윈도우 쪽 CPU 경합까지 겹쳐서 매번 복구에 약 10분이 걸렸다. 그 사이 사이트는 두 번 530이었다(합계 약 22분). 11-06 장애도 집컴 쪽이었다. DB가 있는 기기가 가장 약한 기기였던 셈이다.

## 결정

- 앱·DB·Redis·lora-server·임베딩을 모두 노트북(`teagy`)에서 돌린다. 집컴은 완전히 내린다.
- DB·Redis는 노트북 도커(저장소 루트 untracked `docker-compose.yaml`, 포트 5432·6379)에서 돌린다. `.env`의 `localhost:5432`와 k3s `external-db-redis.yaml`은 그대로 쓴다.
- GPU는 Ollama 7.8B·2.4B와 lora가 나눠 쓰고, 임베딩은 CPU 변형 `bge-m3-cpu`로 돌린다.
- 끄기·켜기는 노트북 한 대 기준으로 바꾼다. 끄기는 앱 → Arda → DB(정상 종료) → 스위치 순서다. 켜기는 어드민이 아니라 바탕화면 `서버 켜기`로 한다.
- 판단기(serve-agent·standby-agent), `desktop-link`, `sync-standby.sh`, 집컴 스위치는 삭제한다.

## 배제한 대안

- 집컴 예비 유지: 장애의 원인이 바로 집컴 DB였다. 예비 서버가 오히려 단일 장애점이었다.
- 리허설 후 전환: 집컴이 20~60분마다 쓰러지는 상황이라 덤프를 두 번 받는 것 자체가 위험했다. 덤프 한 번으로 바로 전환했다.
- 유료 관리형 DB·클라우드: 무료 원칙과 09-29 결정(온프레미스 유지)에 어긋난다.

## 대가

- 노트북이 꺼지거나 덮이거나 집 밖이면 사이트 전체가 꺼진다.
- 바깥 백업이 없다. 전환 시점 덤프는 집컴 볼륨·`~/backups`·OneDrive에 남아 있다.
- VRAM이 거의 꽉 찬다(약 7.9/8.2GB).

## 결과·확인

- 다운 16:49~16:58(약 9분). 69개 테이블 행 수가 덤프와 모두 같았다. 임베딩은 저장된 벡터와 코사인 0.99999였다. lora 응답은 200·약 2초였다.
- mova 28질의 하네스는 25/28이었다. 실패 3건은 이해 모델의 분류 오류이고 전환과 무관한 것으로 판단했다(미확정). 상세는 `WORK_LOG_MAINPAGE.md` 11-08.
