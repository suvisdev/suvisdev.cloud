# mova 추천 품질 검증 — Phase 1 (EC2 Gemini 경로)

**범위**: EC2 백엔드(`RECOMMENDATION_BACKEND=gemini` 경로)만 대상. 실행 환경(학원
PC)에는 GPU·LoRA 서버 접근이 없어 `RECOMMENDATION_BACKEND=lora` 경로는 이번
Phase에서 검증 불가 — 별도 Phase(집, GPU)로 분리. `hub_knowledge`는 EC2에
Ollama가 없어 여전히 0건(백로그 "EC2 hub_knowledge 임베딩 어댑터 부재"와
동일 원인) — 이번 골든셋 응답은 hub_knowledge RAG 없이 카탈로그(movies/
actors/characters/tags)만으로 나온 결과라는 전제로 판정한다.

## 0. 사전 확인 — 응답 구조·DB 제약

**`/mova/chat` 요청/응답**(`market_chat_router.py`, `market_chat_schema.py`)
- 요청: `{message: str, history: list[dict], model?: "flash"|"flash15"|"pro", user_id?: int}`
- **인증 없음** — `require_auth.py`(`get_current_user`)가 이 라우터에 안 걸려
  있음, IP 기준 rate limit(`chat_rate_limit`, 60초당 20회)만 있음. 즉 로그인
  없이 그대로 POST 가능(§2에서 실제로 무인증 호출). 이미 알려진 백로그
  "LLM 챗 엔드포인트 무인증" 항목과 같은 계열 — mova는 그나마 rate limit이
  있는 유일한 케이스.
- 응답: `{reply, recommendations[], refined_query, keywords, intent_type,
  search_filters}`. `recommendations[]` 필드: `id`(슬러그), `movie_id`(DB
  매칭 시 int, **매칭 실패 시 null**), `title`, `year`, `poster`, `synopsis`,
  `platform`, `hook`. **`movie_id`가 null이면 우리 카탈로그에 없는 영화를
  Gemini가 자유 지식으로 추천했다는 뜻** — 이번 검증에서 "환각 여부"를
  가르는 실질적 신호로 이 필드를 썼다(§3 판정 근거 참고).

**intent 분류 — 2단계**(`market_chat_interactor.py`)
1. 라우팅 분류(`crud`/`rag`/`general`, Qwen 기반) — `general`/`crud`면 RAG·
   추천 전체를 스킵하고 바로 Gemini 잡담 응답으로 감. **로그에만 남고
   응답 필드엔 노출 안 됨**(`logger.info("[ChatInteractor] trace=%s
   destination=%s", ...)`) — 이번 골든셋은 전부 추천 요청이라 이 로그는
   확인 안 함(불필요).
2. 의도 추출(`refined_query`/`keywords`/`intent_type`/`search_filters`) —
   **응답 `intent_type` 필드로 그대로 노출**되므로 컨테이너 로그 없이
   API 응답만으로 검증 가능했다.

**카드 vs 산문 분기**(`chat_reply.py::parse_gemini_reply`/`_extract_json`):
프롬프트가 `{"intro":..,"picks":[...]}` JSON을 요구하지만 **런타임 강제
(function calling/response_schema)가 없다** — JSON 파싱 실패 시
`intro=raw.strip()[:300]`(산문 그대로), `recommendations=[]`로 반환되는 게
"산문 회귀" 코드 지점. **이번 15회 실행에서는 전부 유효 JSON으로 파싱돼
산문 회귀가 0건 관측됨**(§3 참고) — 가능성은 있으나 이번 표본에서는 발생 안 함.

**`RECOMMENDATION_BACKEND` — 실행 전 발견한 배포 갭**: 코드 기본값이
`"lora"`(`market_chat_provider.py:41`)인데 **EC2 `.env`엔 이 변수가 아예
없었음** — 즉 이번 조사 시작 시점까지 EC2 mova chat은 (호출된 적이
있었다면) 붙지도 않는 집 GPU `lora_server`를 매번 호출하려다 실패하는
상태였을 가능성이 높다. 골든셋 실행 전 `RECOMMENDATION_BACKEND=gemini`를
EC2 `.env`에 추가 + `docker compose up -d backend`로 반영 후 진행(§2).
**백로그**: 이 갭 자체를 별도 항목으로 남긴다(아래 "다음에 할 일" 참고).

**`movies` 테이블 실제 컬럼**(`studio_movies_orm.py`): `slug`, `title`,
`release_year`, `rating`, `poster_url`, `platforms`, `age_rating`,
`embedding`, `collection_id`. **`runtime`(상영시간)·`origin_country`(제작국)
컬럼이 없다** — 15번 쿼리의 "상영시간 짧은"과 9번의 "한국"은 시스템이
원천적으로 정확히 지킬 수 없는 조건이라는 전제로 판정 기준을 낮춘다(§1).

장르는 `movies.genres` 컬럼이 아니라 `tags`(`tag_kind='genre'`) 조인
테이블에 저장된다(`movies_pg_repository.py::_replace_genre_tags`) — 장르
필터링 자체는 DB 레벨에서 검증 가능. `mood` 태그는 bulk import 경로가
안 채워 **사실상 0건** — 무드/맥락 카테고리(§1의 11~13번) 판정은 DB 필드
대조가 아니라 정성적 판단에 의존한다.

## 1. 골든셋 (15개)

각 쿼리의 "좋은 응답 기준"은 공통 기준 + 쿼리별 추가 기준으로 구성한다.

**공통 기준(모든 쿼리에 적용)**
- (C1) 카드 3개 구조화 응답(산문으로 뭉뚱그려 답하면 형식 회귀)
- (C2) 언급된 영화가 실제 `movies` 테이블에 존재(환각 없음)
- (C3) 카드 3개의 감독이 서로 겹치지 않음(다양성 — 동일 감독 3연작만 긁어오는 것 방지)
- (C4) 요청한 명시적 조건(장르·배우·연도)은 DB로 검증 가능한 한 반드시 준수

**판정 기준 재확인(2026-08-05 grounded prompting 적용 후 — 다음 재판정 시
반드시 이 규칙을 따를 것)**: movie_id 기반 grounding 도입 이후 시스템이
"카탈로그에 없으면 억지로 3개를 채우지 않고 있는 만큼만 반환"하도록
의도적으로 바뀌었다(§6). 따라서 **카드 개수가 3개 미만이어도 있는 카드가
전부 정확하면 통과**로 판정한다(C1의 "카드 3개"는 "카드 0~3개, 산문 아닌
구조화 응답"으로 완화 해석). 세 등급의 정확한 구분:
- **통과**: 카드가 1~3개 있고, 있는 카드는 전부 grounded(movie_id 有) +
  요청 조건(C4) 충족. **카드 0개는 원칙적으로 "카드 0개"는 자동 통과가
  아니라 실패(아래 참고)** — 단 14번처럼 §1.5에서 쿼리별로 명시적으로
  "되묻기/0개도 통과"를 예외로 정의해둔 경우에 한해서만 그 쿼리의
  완화된 기준을 따른다(일반화해서 다른 쿼리에 적용하지 말 것).
- **부분**: 반환된 카드 중 일부는 grounded+정확, 일부는 조건 위반(연도
  이탈 등) 또는 null(ungrounded)로 섞여 있음.
- **실패**: 반환된 카드가 0개(커버리지 부족으로 정직하게 못 찾음 포함)
  이거나, 반환된 카드가 있어도 전부 조건 위반/오귀속.

### 1.5 엣지 케이스 (2개)

> 사용자가 예시 3개(`영화 추천`/`재밌는 거 뭐 있어`/`1편에 상영시간 짧은 SF

> + 하이퍼-구체 쿼리** 2개만 채택했다. "영화 추천"은 골든셋에서 제외.

## 2. 실행 — `/mova/chat` 실제 호출 결과

**로그인 관련**: §0에서 확인했듯 무인증 엔드포인트라 로그인 절차 자체가
불필요 — 아래 스크립트 그대로 바로 호출 가능. 15개 전부 IP rate
limit(60초당 20회) 안에 들어가도록 4초 간격으로 순차 실행, 전부 `200 OK`.

**재실행용 스크립트(그대로 복붙 가능)** — 쿼리 순서·번호는 §1과 동일:

```bash
mkdir -p /tmp/mova_phase1_rerun && cd /tmp/mova_phase1_rerun

declare -a QUERIES=(
  "액션 영화 추천해줘"                                             # 1
  "잔잔한 로맨스 영화 뭐 있어"                                     # 2
  "무서운 공포 영화 추천"                                          # 3
  "웃긴 코미디 영화 알려줘"                                        # 4
  "전지현 나오는 코미디"                                           # 5
  "송강호 출연 스릴러 영화"                                        # 6
  "키아누 리브스 액션 영화"                                        # 7
  "80년대 SF 영화"                                                 # 8
  "2020년대 한국 액션 영화"                                        # 9
  "90년대 로맨스 영화"                                             # 10
  "가족과 볼 만한 영화"                                            # 11
  "혼자 볼 감성적인 영화"                                          # 12
  "스트레스 풀고 싶을 때 볼 영화"                                  # 13
  "재밌는 거 뭐 있어"                                              # 14
  "1편에 상영시간 짧은 SF 드라마이면서 여자 주인공 인생역전 스토리"  # 15
)

i=1
for q in "${QUERIES[@]}"; do
  fname=$(printf "q%02d.json" "$i")
  payload=$(python3 -c "import json,sys; print(json.dumps({'message': sys.argv[1], 'history': []}))" "$q")
  http_code=$(curl -s -m 30 -o "$fname" -w "%{http_code}" \
    -X POST https://api.suvisdev.cloud/mova/chat \
    -H "Content-Type: application/json" -d "$payload")
  echo "q$i [$http_code] $q"
  i=$((i+1))
  sleep 4
done
```

**결과 확인**(각 `qNN.json`에서 `intent_type`·`recommendations[].movie_id`
읽기):

```bash
for f in q*.json; do
  echo "=== $f ==="
  python3 -c "
import json
d = json.load(open('$f'))
print('intent_type:', d.get('intent_type'))
print('reply:', d.get('reply')[:100])
for r in d.get('recommendations', []):
    print(' -', r.get('movie_id'), r.get('title'), r.get('year'), '| hook:', (r.get('hook') or '')[:50])
"
done
```

**grounding·환각 여부 DB 대조**(`movie_id`가 가리키는 실제 DB 행 확인 —
EC2 `suvisdevcloud-db-1` 컨테이너에서):

```bash
docker exec suvisdevcloud-db-1 psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "
select m.id, m.title, m.release_year,
  coalesce(string_agg(distinct t.label, ', ') filter (where t.tag_kind='genre'), '') as genres
from movies m left join tags t on t.movie_id = m.id
where m.id in (여기에 응답에서 나온 movie_id들 콤마로)
group by m.id, m.title, m.release_year order by m.id;
"
```

의도와 안 맞으면) 오귀속 의심 — §3·§6의 "괴물"/"극한직업" 사례가 바로 이
대조로 잡혔다.

**⚠ 핵심 발견 — 6번 쿼리의 배우 오귀속(title-collision 매칭 버그)**: DB
`id=426`(`slug=tmdb-1091`)을 TMDB에서 직접 조회하면 원제 `The Thing`
(1982, 존 카펜터 감독)이고 **송강호가 출연한 적 없는 영화**다. 우리 DB의
한국어 로컬라이즈 제목이 봉준호 감독의 `괴물`(2006, 송강호 주연)과 똑같이
"괴물"이라서, Gemini가 (아마도 봉준호의 "괴물"을 의도하고) 제목만으로
언급한 걸 백엔드의 제목 매칭이 **동명이인 영화로 잘못 연결**한 것으로
추정된다. 이건 "지어낸 영화"(고전적 환각)가 아니라 **"실재하는 DB row에
잘못 연결된 진짜 오귀속"** — `movie_id`가 있다고 해서 그 카드가 항상
맞다는 보장이 없다는 뜻이라 오히려 null보다 더 위험한 실패 모드다.

**부수 발견 — 제목 포맷 하나로 매칭이 깨짐**: 4번 쿼리에서 "빽 투 더
퓨쳐"는 `movie_id=194`로 정확히 매칭됐는데, 8번 쿼리에서 Gemini가 같은
영화를 "빽 투 더 퓨쳐 (1985)"로(연도 접미사 포함) 언급하자 매칭이 실패해
`movie_id=null`이 됐다. 제목 매칭이 정확히 일치하는 문자열에만 의존하는
것으로 보이며, 연도 접미사 같은 사소한 포맷 차이에도 깨지는 취약한 구조.

## 4. hub_knowledge 임베딩 백필 절차 (사전 조사만 — 미실행)

**진입점은 이미 있다**: `suvisdev/scripts/ingest_hub_knowledge.py`
(2026-08-02 신설, `backfill_hub_knowledge_cli.py`류 별도 이름의 CLI는
없음 — 이 스크립트가 유일한 진입점). 실행: `docker compose exec backend
python scripts/ingest_hub_knowledge.py`(또는 로컬 venv에서 직접).

**동작 방식**: `MoviesPgRepository.list_movies(MovieFilterQuery(limit=100))`
로 movies를 순회 → 영화당 `CharactersPgRepository.get_cast_by_movie()`로
출연진 상위 5명 + 감독명 조회 → `개봉/장르/출연/감독` 텍스트를 조합해
`HubRagInteractor.ingest_movie()` 1회 호출(내부에서
`OllamaEmbeddingAdapter.embed()` 1콜 = 영화 1편, 배치 임베딩 아님) →
루프 끝에 `session.commit()` 1회.

**Phase 2 실행 전 반드시 확인/수정할 것 — 이번 조사로 발견한 2가지**:

1. **`limit=100` 하드코딩**: 지금 mova 카탈로그는 오늘 배치로 1055편까지
   늘어났는데(§ 관련 WORK_LOG 2026-08-05), 이 스크립트를 그대로 돌리면
   **처음 100편만** 처리되고 나머지 955편은 조용히 스킵된다. `MovieFilterQuery`
   가 `offset`도 지원하니(수정 없이 바로 가능) `limit`을 늘리거나(예:
   `limit=2000`, 총량보다 넉넉하게) `offset`을 증가시키며 반복 호출하는
   래퍼가 필요 — 이번 스코프에선 코드 수정 안 함, Phase 2 착수 시 처리할 것.
2. **루프 끝 단일 커밋 + rollback 없는 except — 오늘 고친 도미노 패턴과
   동일한 위험**: `try/except`가 영화당 있긴 하지만 실패해도 `print`만
   하고 `session.rollback()`을 안 부른다. Ollama 임베딩 실패(`HubRagError`)
   자체는 DB에 안 닿아서 세션을 오염시키지 않을 가능성이 높지만,
   `HubKnowledgeRepository.upsert()`의 flush가 다른 이유(예: 데이터 길이
   등 다른 제약)로 실패하면 오늘(2026-08-05) `bulk_import_movies.py`에서
   겪은 것과 **완전히 같은 메커니즘의 도미노**가 재발할 수 있다. 1000편
   규모에서 이 리스크를 방치하는 건 위험도가 높아졌으니, Phase 2 착수 전
   각 except 블록에 `await session.rollback()` 한 줄 추가를 권장(이번
   세션에서 검증된 동일 패턴).

**소요 시간 추정 — 실측 자료 없음, "실측 필요"**: 코드·로그 어디에도
`nomic-embed-text` 임베딩 콜 자체의 타이밍 벤치마크나 주석이 없다(§
코드 조사 결과 확인). 일반적으로 이 모델은 파라미터 수가 작아(~137M)
CPU에서도 텍스트 1건당 수백 ms대가 보통이지만, 이건 **일반론이지 이
호스트에서의 실측이 아니다** — 인용할 로컬 벤치마크 자료가 없으므로
정확한 숫자 대신 "실측 필요"로 남긴다. Phase 2 착수 시 **5편만 먼저
`time` 찍어서 편당 평균을 낸 뒤 전체(1055편 기준) 예상 시간을 역산하는
것**을 권장 — 예를 들어 편당 1초면 총 ~18분, 편당 3초면 총 ~53분로 편차가
커서 사전 추정보다 소규모 실측이 훨씬 신뢰도 높다.

**Phase 2 실행 체크리스트(정리)**
1. 홈 GPU 머신에서 `ollama list`로 `nomic-embed-text` 보유 확인 — 이전
   조사(오늘 세션 시작 시점)에서 이 호스트엔 `qwen3:8b`/`exaone3.5:*`만
   있고 `nomic-embed-text`는 없었다(`ollama pull nomic-embed-text` 필요할
   수 있음 — Phase 2 시작 시 재확인).
2. `ingest_hub_knowledge.py`의 `limit=100` → 전체 커버하도록 수정(또는
   offset 루프).
3. `except` 블록에 `session.rollback()` 추가(도미노 방지, 이번 세션에서
   검증된 패턴).
4. 5편 시험 실행으로 편당 소요시간 실측 → 전체 예상 시간 역산 후 본실행.
5. 완료 후 `hub_knowledge` row count가 movies 수(비-tmdb slug 제외)와
   맞는지 확인.

**배포 직후 검증 중 세 번째 버그 추가 발견**: DB 존재 여부만 확인하는
첫 구현은 "Gemini가 title/hook은 실제 의도한 영화(예: 극한직업) 설명
그대로 두고 movie_id만 카탈로그에 없는 엉뚱한(그러나 DB엔 실존하는 다른
영화, 예: 캡틴 아메리카) 값을 끼워 보내는" 패턴을 못 걸렀다 — `movie_id`
가 유효한 DB row를 가리키기만 하면 통과시켰기 때문에, "제목은 A인데
실제로 링크되는 건 B"인 카드가 나갈 뻔했다. `enrich_from_db()`에 "실제로
제시한 카탈로그 id 집합에도 속하는가" 검증을 추가(DB 존재 여부만으론
불충분했다는 걸 이 세션에서 직접 실증)하고, 최종 `title`도 항상 DB 값으로
덮어쓰는 안전망을 더해 재배포 후 재검증했다.

### 7.2 재분류 — #14, #6

**#14 "재밌는 거 뭐 있어" — 통과 → 실패**: 이번 응답은 `reply`가 "시간
가는 줄 모르고 즐길 수 있는 재밌는 영화들을 모아봤습니다"라고 **추천을
전달했다고 주장**하면서 `recommendations: []`(카드 0개)를 반환했다.
§1.5의 완화 기준("카드 0개는 되묻기 또는 인기작 위주 카드 3개일 때만
예외로 통과")을 문자 그대로 적용하면 이번 응답은 **되묻기도 아니고
카드 3개도 아니라서 예외 요건 미충족** — 실패로 재분류한다. 이는
새로운 버그가 아니라 §6 말미에 이미 기록해 둔 "reply 텍스트와 picks
개수 불일치" 버그가 실제로 판정을 뒤집은 첫 사례다.

**#6 "송강호 출연 스릴러" — 통과 판정의 신뢰도 재검토 필요**: §7.3의
근본 원인 조사 결과, `search_tag_catalog()`는 **배우 이름을 전혀
검색하지 않고 장르/무드 태그로만 후보를 만든다.** 즉 #6이 두 사이클
연속 "통과"였던 건 시스템이 "송강호"를 이해해서가 아니라, **기생충이
마침 스릴러 태그 평점 상위권에 있으면서 우연히 송강호가 주연이었다**는
우연의 일치다. 다른 배우·다른 스릴러 조합이었다면 똑같이 실패했을
가능성이 높다 — 골든셋의 배우 지정 쿼리(5·6·7번) 3건 중 통과로 집계된
1건(#6)도 사실상 매칭 로직이 아니라 데이터 분포의 우연에 기댄 결과였다는
뜻이다. 기존 "통과 8~9건"의 신뢰도를 이 관점에서 다시 봐야 한다.

### 7.3 근본 원인 — `search_tag_catalog()`(왜 카탈로그를 늘려도 안 풀렸나)

`market_chat_pg_repository.py::search_tag_catalog()`:

```python
cond = or_(*[MovaTag.label.ilike(f"%{kw}%") for kw in keywords[:6]])
... .order_by(MovaMovie.rating.desc()).limit(limit)  # limit=12
```

Gemini가 응답에 실을 수 있는 `movie_id`는 이 함수가 만든 후보
목록(최대 12개)에 있는 것으로 사실상 제한된다(grounded prompting 설계상
후보 밖의 id는 카탈로그 존재 검증에서 걸러짐). 이 함수의 구조적 한계
4가지가 오늘 실패 6건을 전부 설명한다:

1. **배우 이름 미지원**: `MovaTag`(장르/무드 라벨)만 검색 대상이고
   배우·감독 이름은 애초에 이 쿼리가 보는 테이블에 없다. "전지현"·
   "키아누 리브스"·"송강호" 같은 키워드는 매칭 조건에 전혀 기여하지
   못하고, 결과는 순수하게 장르 키워드(코미디/액션/스릴러)만으로
   추려진 상위 12개다. → #5·#7 실패의 직접 원인, #6 통과가 우연인
   이유(§7.2).
2. **top-12 rating 컷**: 태그가 맞아도 평점 순위가 12위 밖이면 후보에서
   탈락한다. 실측: "스피드"(`tmdb-1637`, 1994, 액션·스릴러 태그
   보유)가 액션 태그 영화 rating 상위 15개 조회에도 안 잡힘 — top-12
   윈도우 밖이라 Gemini가 이 영화를 볼 기회 자체가 없었다. → 카탈로그에
   정식으로 들어와 있어도(§7.4) 이 컷 때문에 소용없다는 뜻.
3. **키워드 OR 결합**: `or_(...)`라 키워드 중 하나만 태그에 걸려도
   후보에 들어간다 — "SF"+"드라마" 같은 복합 조건(#15)의 진짜 교집합을
   만들지 못한다. top-12 안에 두 조건을 동시에 만족하는 후보가 없으면
   그대로 0개.
4. **`origin_country` 컬럼 부재**(기존에 이미 알려진 이슈, §0 참고):
   "한국"(#9) 같은 국가 조건은 이 함수뿐 아니라 스키마 자체에 검증
   수단이 없다.

**카탈로그 확장 트랙 종결**: 위 4가지는 모두 데이터 볼륨과 무관한
후보 생성 로직의 구조적 한계다. TMDB popular 페이지를 추가로(103페이지
이상) 수집해도 이 6건 실패는 그대로일 것으로 판단 — 카탈로그 확장은
이번 재검증으로 실증 종결하고, 레버리지는 `search_tag_catalog()` 개선
(배우 조인·top-N 컷 완화·키워드 AND 옵션)과 데이터 정합성(아래 §7.4)
쪽으로 옮긴다.
