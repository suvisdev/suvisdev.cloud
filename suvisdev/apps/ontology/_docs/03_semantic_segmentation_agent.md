# 03. 시맨틱 분할 에이전트 — "Loom"

> ⛔ **제외됨 (2026-07-27)** — 용도 재정의("보도 유무/폭" 구조 신호)까지
> 검토했으나, 관문0 실측 결과 **보도 신호 자체가 서울 OSM에 존재하지 않음**
> (`sidewalk=*` 0.4~1.2%, 커버리지 보도/도로 = 0.04, `width` 전무). 관문1
> (스트리트뷰+CV)도 소비처 walk 그래프가 데모(4간선)+전 간선 이미지 비용
> 문제로 회귀 → 04·08과 동급 정식 제외. 상세 근거: 아래 §5.4. 실제 제품
> 수요·데이터 경로가 생기면 재검토.

> **에이전트 이름 추천**: **Loom** (베틀 — 픽셀 단위로 이미지를 짜서 영역을 나눈다)
> 파일명: `semantic_segmentation_interactor.py`
> **원논문**: PSPNet (CNN) → **최신 대체**: SegFormer-B0 (트랜스포머) — LoRA 적용 가능
> **공통 규약(00_COMMON_conventions.md)을 먼저 읽어라.**

---

## 1. 모델 선택 근거

| 후보 | 아키텍처 | QLoRA/LoRA | 3050 8GB | 추천도 |
|------|---------|-----------|----------|--------|
| PSPNet (원논문) | CNN | ❌ | full ft만, 무거움 | 구식 |
| **SegFormer-B0** | 트랜스포머(경량) | ✅ LoRA | ✅ 실용적 | ⭐ 1순위 |
| Mask2Former | 트랜스포머 | ✅ | ⚠️ 8GB 빡셈 | 무거움 |

**결정**: **SegFormer-B0**. MiT 백본이 트랜스포머라 LoRA를 attention에 붙일 수 있고, B0는 가장 경량이라 3050에 맞음. `transformers`의 `SegformerForSemanticSegmentation` 사용.

## 2. 데이터셋 준비 가이드

시맨틱 분할은 **픽셀별 마스크**가 필요하다 (박스가 아님).

**형식**:
```
dataset/
  images/
    train/  img001.png ...
    val/    ...
  masks/
    train/  img001.png ...   # 각 픽셀값 = 클래스 id (0,1,2,...), 팔레트 PNG
    val/    ...
```
- 마스크는 **이미지와 동일 크기**, 픽셀값이 클래스 인덱스
- 배경도 하나의 클래스(보통 0)

**라벨링 도구**: CVAT, Roboflow(segmentation), Segment Anything(SAM)으로 반자동 마스크 생성 후 보정

**데이터 규모**:
| 이미지 수 | 기대치 |
|-----------|--------|
| ~100 | 데모 |
| 300~800 | 실용 ✅ |
| 1000+ | 안정 |

**주의**: 분할은 라벨링 비용이 태스크 중 가장 큼. SAM으로 초벌 마스크 뽑고 사람이 수정하는 워크플로우 강력 추천 → md H2에 반영.

## 3. Harness 단계

- **H0**: `transformers`, `datasets`, `evaluate`, `peft`(LoRA) 설치. SegFormer-B0 로드 확인.
- **H1**: VRAM 실측. 분할은 고해상도라 메모리 큼 → **imgsz 512 이하, batch 2~4**로 시작, OOM이면 512→384.
- **H2**: 데이터셋 검증. 마스크-이미지 크기 일치, 클래스 인덱스 범위 확인. SAM 초벌 마스크 파이프라인(선택).
- **H3**: LoRA 파인튜닝
  - `peft`로 SegFormer attention에 LoRA 부착
  - loss: cross-entropy(픽셀별), metric: mIoU
  - **best mIoU 체크포인트 저장**
- **H4**: 추론 어댑터 — `SegmenterPort.segment(image_bytes) -> SegmentationResult` (mask 배열 + 클래스별 영역)
- **H5**: MCP tool
  ```python
  @mcp.tool()
  async def segment_image(image_b64: str) -> dict:
      """이미지를 픽셀 단위로 분할해 각 영역의 클래스와 마스크를 반환한다.
      '이 이미지 영역별로 나눠줘', '어디가 무엇인지' 요청에 사용.
      반환: 클래스별 영역 비율 + (선택)마스크 오버레이 base64."""
  ```
- **H6**: 시스템 프롬프트
  ```
  너는 시맨틱 분할 에이전트 Loom이다.
  - 이미지의 영역 구분을 물으면 segment_image를 사용한다.
  - 클래스별 면적 비율을 요약하고, 필요시 마스크 시각화를 제공한다.
  ```

## 4. Gate 요약
- H1: VRAM + 해상도/batch 상한
- H2: 마스크-이미지 정합성 통과
- H3: val mIoU 로그 + 체크포인트
- H4: 포트 통해 마스크 결과 반환
- H5: tool 호출 성공
- H6: 자연어 질의 → 영역 분할 요약 응답

## 5. gildle 재정의 검토 (2026-07-23) — 보류

`00_COMMON_conventions.md` §8 감사에서 mova 포스터 도메인엔 용도가 없다고
판정됐으나, gildle에 이미 `HazardZone`(결빙 교통사고 다발지역) 엔티티가
있어 "도로 이미지를 분할해 보도/차도/결빙을 구분하고 라우팅 가중치로
쓸 수 있는가"를 별도로 검토했다. 06의 실패 원인(마지막 단계 — 결과를
실제로 어떻게 쓰는지 — 가 불명확한 채 착수)을 기준으로 4개 항목을 봤다.

### 5.1 결빙 세그멘테이션 — 기각

Cityscapes/Mapillary Vistas 등 실제 거리 장면 세그멘테이션 데이터셋에는
`road`/`sidewalk`/`vegetation` 같은 **구조적** 클래스만 있고 **"결빙"
클래스 자체가 없다.** 결빙은 계절·기상에 따라 수시로 바뀌는 **일시적**
현상이라, 특정 시점에 촬영된 정적 스트리트뷰 한 장으로 "지금 이 길이
얼었는지"를 판정하는 것과는 전혀 다른 문제다(사실상 실시간 기상 문제).
**세그멘테이션으로 결빙을 직접 잡는다는 원래 아이디어는 기각** — gildle의
기존 결빙 신호(한국도로교통공단 결빙 사고 통계 CSV, `HazardZone`)는 그대로
유지하는 게 맞다.

### 5.2 대안: 보도/차도 구조 분할 — 기술적으로는 가능하나 전제조건 미해결

결빙 대신 "이 도로에 보도가 있는가/폭이 얼마인가" 같은 **계절 무관 구조
신호**라면 Cityscapes/Mapillary로 학습된(또는 사전학습된) SegFormer로
잡을 수 있는 영역이다 — 포스터에 COCO를 억지로 붙이는 것과 달리 실제
거리 장면 데이터셋이라 도메인이 일치한다는 사용자 지적은 타당하다. 다만
검토 항목 4개 중 마지막(라우팅 반영)만 명확하고, 나머지는 안 풀렸다:

| 항목 | 상태 |
|------|------|
| 라우팅에 반영하는 방법 | **명확**: `RouteWeightCalculator._near_hazard`와 동일한 패턴(간선 중간좌표 근접 매칭)으로 "보도 없음/좁음" 판정을 계절 무관 상시 페널티로 추가하면 기존 구조에 자연스럽게 얹힌다. |
| 이미지 수집 경로 | **미확정**: gildle의 Kakao 연동은 주소 지오코딩(`/v2/local/search/address.json`)뿐, 로드뷰/스트리트뷰 이미지 API가 아니다. Google Street View Static API가 가장 표준적인 대안이지만 신규 API 키·과금·ML 학습 목적 사용 시 ToS 확인이 안 됐고, Mapillary는 서울 커버리지가 불확실하다. |
| ERD 연결 지점 | 있음(`RouteEdge`/`HazardZone`과 같은 층위에 새 구조적 신호 추가) — 다만 위 이미지 수집이 안 풀리면 의미 없음. |
| 결빙 라벨 확보 가능성 | §5.1에서 기각 — 애초에 "결빙"이 아니라 "보도 유무"로 스코프가 바뀐다는 전제 자체를 사용자와 다시 맞춰야 함. |

추가로 확인 안 된 것: gildle의 실제 보행로 그래프는 아직 `data/sample_walk_graph.json`
(4개 간선짜리 데모)뿐이고 "운영은 OSM(osmnx, `network_type='walk'`)"은
README상 계획일 뿐 아직 구현 전이다. OSM이 한국 보도를 얼마나 별도
way로 태깅해뒀는지(있으면 CV 없이 공짜로 같은 신호를 얻을 수도 있다)도
확인 안 됨 — 세그멘테이션을 붙이기 전에 "OSM만으로 이미 충분한가"부터
봐야 중복 투자를 피한다.

### 5.3 결론 — 착수하지 않음

이미지 수집 경로(가장 큰 미확정 요소)와 OSM 대비 한계효용이 안 풀린 채로는
사용자가 정한 기준("마지막이 명확하지 않으면 착수하지 말 것")에 못 미친다.
**현재 스코프대로 착수하지 않는다.** 재검토 조건: (1) 서울 스트리트뷰
이미지를 합법적·안정적으로 확보할 경로 확정, (2) OSM 기존 보도 태깅으로
이미 커버되는지 확인해 CV의 한계효용이 남아있는지 확인.

### 5.4 관문0 실측 (2026-07-27) — OSM 경로 폐기

§5.2 재검토 조건 (2)를 Overpass API로 실측했다. 합의한 관문 구조(비용 낮은
순으로 각 관문서 폐기 가능): **관문0** = OSM 서울 walk가 보도를 별도
way/태그로 이미 주면 CV 불필요 → 폐기.

**측정 (overpass-api.de, 서울 3개 지역):**

| 지역 | 도로 | `sidewalk=*` 속성 | `footway=sidewalk` way | `width` 태그 |
|------|------|-------------------|------------------------|--------------|
| 강남 | 903 | 11 (1.2%) | — | — |
| 성북 주거 | 1127 | 5 (0.4%) | 131 (footway 545 중) | 5 |

**커버리지 실측** (성북 소구역): 도로 643 way / 96.85km vs `footway=sidewalk`
25 way / 3.47km → **보도길이/도로길이 = 0.04**. 완전 양방향 매핑이면 ~2.0,
편측 완전이면 ~1.0인데 0.04 → 도로 길이의 **약 96%에 매핑된 보도가 없다.**

**판정:**
1. `sidewalk=*` 도로 속성(`RouteWeightCalculator`가 간선별 보도 페널티에
   바로 쓸 유일한 태그)은 사실상 전무(0.4~1.2%). `width` 태그도 전무 →
   재정의 용도 '폭'은 OSM에서 못 얻는다.
2. 스코프를 '유무'로만 좁혀도 살아나지 않는다. (a) 개념: OSM은 open-world라
   "보도 매핑 없음 ≠ 보도 없음" — "보도 없음→페널티" 규칙이 요구하는 *부재*를
   신뢰할 수 없다. (b) 실측: 커버리지 4% → 페널티가 도로 ~96%에 발화 = 노이즈.
   신뢰 가능한 *존재* 신호는 walk 그래프가 이미 그 보도 간선으로 라우팅하므로
   대체로 중복이다.

**결론: 04·08과 동급의 정식 '폐기/제외'.** 보도 신호 자체가 서울 OSM에
존재하지 않음이 실측으로 확인됐고, 이는 "그러니 CV가 필요하다"로 이어지지
않는다 — 남은 관문1(스트리트뷰+CV)조차 소비처 walk 그래프가 데모(4간선,
OSM 인제스트 미구현)이고 CV는 실 그래프의 전 간선 이미지가 필요해 관문1
이미지 수집 비용 문제로 회귀한다. **(2026-07-27 사용자 최종 확정 — 제외.)**
