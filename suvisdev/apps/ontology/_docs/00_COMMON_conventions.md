# 공통 규약 (모든 에이전트 md 공유)

> 2~8번 각 에이전트 md는 이 파일을 **먼저 읽고** 개별 지시를 따른다.
> Claude Code는 각 작업 시작 시 이 규약을 준수한다.

---

## 1. 하드웨어 제약 (절대 기준)

- **GPU: RTX 3050, VRAM 8GB** ← 모든 설계의 최상위 제약
- **온프레미스 3050 단일에서 전부 실행** (파인튜닝 + 추론)
- **모든 파인튜닝은 8GB 안에서 끝나야 함**: batch size 작게 시작(1~4), gradient accumulation 활용, mixed precision(fp16/bf16) 기본

### 1.1 VRAM 점유 정책 (2026-07-23 확정)

이 서버에는 **`lora-server`(systemd user 서비스, mova 채팅용 EXAONE-3.5-2.4B AWQ LoRA)가
상시 기동**돼 있다(`enabled` — 부팅마다 자동 시작). 기동 시점에 모델을 로드해 프로세스
생존 기간 내내 VRAM에 상주시키는 구조(`model_servers/lora_server/serve.py`의
`lifespan`)라, **다른 학습을 시작하기 전엔 반드시 내려야 한다.**

**실측 관련 주의**: 이번 점검에서 `nvidia-smi`가 같은 세션 안에서도 같은 프로세스에
대해 290MB↔7975MB로 크게 다른 값을 보고했다(WSL2 GPU 패스스루의 계측 불안정으로
추정 — `lora-server`가 재시작되거나 언로드된 정황은 로그에 없었음). **`nvidia-smi`의
"free" 수치만 보고 학습 가능 여부를 판단하지 말 것** — 항상 아래 절차대로 명시적으로
내렸다 올린다.

**모든 파인튜닝(H3) 전 필수 절차** (Echo/07에서 이미 검증된 패턴):

```bash
# 1) 점유 서비스 정지
systemctl --user stop lora-server
# Ollama도 확인(요청 시 온디맨드 로드/유휴 시 자동 언로드라 보통 비어있지만, 확인 습관화)
ollama ps

# 2) VRAM 확보 확인(참고용 — 위 주의사항대로 100% 신뢰하지 않는다)
nvidia-smi --query-gpu=memory.used,memory.free --format=csv

# 3) 학습 실행

# 4) 완료 후 프로덕션 복구
systemctl --user start lora-server
curl -s http://localhost:8200/health   # model_loaded:true 확인
```

**대안(외부 GPU 분리)**: AWS 도입 전까지는 위 절차가 유일한 방법이다. VRAM이 계속
빠듯한 태스크(예: 05 이미지 생성)는 학습만 외부 GPU로 분리하는 방안을 md에 명시하고
사용자 확인 후 진행한다(§6 AWS 대비 참고).

## 2. QLoRA / LoRA 적용 원칙

| 아키텍처 | 파인튜닝 방식 |
|----------|--------------|
| 트랜스포머 계열 (ViT, DETR, SegFormer, Transformer 등) | **QLoRA/LoRA** (4bit + adapter) |
| 소량 데이터 + 트랜스포머 | LoRA (양자화 없이도 8GB에 맞으면) |
| 학습이 거의 없는 방식 (PatchCore 등) | 파인튜닝 대신 feature memory 구축 |
| GAN/Diffusion 생성 | LoRA(diffusion) 또는 소형 full ft |

**원칙**: 트랜스포머면 QLoRA/LoRA를 1순위로. VRAM 이득이 없거나 구조가 안 맞으면 md에 이유를 명시하고 대안 사용.

## 3. 아키텍처 규약 (SUVIS DDD)

- **헥사고날 클린 DDD**, 데이터 흐름 `Schema → DTO → App → VO → Entity → ORM → DB`
- 기존 프로젝트 구조에 맞춰 아래 위치에 배치:
  ```
  app/
    ports/           # 추상 포트 인터페이스 (태스크별 Port 정의)
    use_cases/       # <task>_interactor.py  ← 에이전트 유스케이스
    dtos/            # 요청/응답 DTO
  adapter/
    outbound/model/  # 모델 추론 어댑터 (포트 구현체)
  ```
- **interactor 패턴 준수**: 기존 `*_interactor.py`(hub_rag_interactor 등)와 동일한 컨벤션
- **DIP**: use_case는 추상 포트에만 의존, 모델 구현체는 주입 → 추후 AWS/다른 모델로 교체 가능
- VO는 frozen dataclass, `from_orm()` 팩토리 패턴(titanic 규약)

## 4. 헤르메스 엔지니어링 (harness 단계)

각 md는 아래 공통 뼈대를 태스크에 맞게 채운다. **순서대로, Gate 통과 후 다음 단계.**

| 단계 | 목표 | Gate(검증 산출물) |
|------|------|------------------|
| **H0** | 환경/의존성/데이터 구조 확인 | import 성공 + 폴더 구조 |
| **H1** | VRAM 예산 실측 | free VRAM + 모델 로드 delta, batch 상한 결정 |
| **H2** | 데이터셋 준비 및 검증 | 데이터 로더가 정상 배치 반환 |
| **H3** | 파인튜닝 (QLoRA/LoRA/기타) | 학습 곡선 + best 체크포인트 |
| **H4** | 추론 어댑터 (헥사고날 포트) | 포트 통해 VO 반환 단위테스트 |
| **H5** | interactor + MCP tool 노출 | tool 목록에 등장 + 호출 성공 |
| **H6** | 에이전트 통합 + 시스템 프롬프트(스킬) | 자연어 질의 → tool 호출 → 응답 |

**금지**: Gate 건너뛰기, 여러 단계 동시 구현, VRAM 실측(H1) 없이 학습 코드 작성.

## 5. "툴과 스킬을 준다"의 의미

- **tool** = MCP 서버가 노출하는 함수 (예: `detect_objects`, `segment_image`)
- **skill** = ① tool의 docstring(언제/어떻게 쓸지) + ② 에이전트 시스템 프롬프트의 행동 규칙
- 각 md의 H5/H6에서 이 둘을 반드시 정성껏 작성

## 6. AWS 대비 (지금은 설계만)

- 곧 AWS 도입 예정 → 포트 추상화만 유지, 실제 구현 미룸
- 이미지/영상 전달은 로컬 경로 대신 **base64 또는 (추후) S3 URL**
- 추론 어댑터를 SageMaker 등으로 교체 가능하게 DIP 준수

## 7. 진행 규칙

- 각 단계 산출물을 사용자에게 보고 후 다음으로
- 데이터셋/환경 관련 불확실한 값은 **추측하지 말고 질문**
- 파인튜닝 방식(QLoRA/full/head) 확정 전 사용자 확인

## 8. 02~08 적합성 감사 (2026-07-23)

06(Sentinel) H3에서 "기법을 먼저 정하고 용도를 나중에 붙이면 도메인 불일치로
무너진다"는 걸 실측으로 확인했다(`06_anomaly_detection_agent.md` §5~§6). 이 md들
자체가 애초에 "기법 → SOTA 모델 → 데이터 형식" 순서로 쓰여 있고 "mova/gildle에
이 문제가 실제로 있는가"는 검증되지 않은 채였다. 그래서 02~08 전체를 아래 세
기준(①용도 ②데이터 ③하드웨어)으로 사전 감사했다 — mova(영화 카탈로그+채팅+
리뷰, 이미지는 포스터 1장/영화뿐)와 gildle(가로수길·결빙구역 라우팅, **이미지
자체가 없는** 순수 지오/테이블 도메인) ERD·문서 기준.

| # | 에이전트 | ① 용도 | ② 데이터 | ③ 하드웨어 |
|---|---------|--------|---------|-----------|
| 02 | Argus(객체 검출) | 위험 | 불확실 | 확실 |
| 03 | Loom(분할) | 위험(§재정의 검토 중) | 위험 | 확실 |
| 04 | Atlas(자세) | **위험 — 제외** | 위험 | 확실 |
| 05 | Prisma(생성) | 불확실 | 확실 | 위험 |
| 06 | Sentinel(이상탐지) | §5~§6 참고(방향 전환 완료) | | |
| 07 | Echo(감정분석) | 확실(완료) | 확실(완료) | 확실(완료) |

**04·08 제외 결정**: mova/gildle 어디에도 "사람 자세/동작"(04)이나 "영상
콘텐츠 처리"(08)를 다루는 파이프라인 지점이 없다 — mova는 포스터(정지 이미지)
+ 텍스트뿐이고 TMDB 트레일러는 외부 링크일 뿐 수집 대상이 아니다. 용도가
없으니 확보할 데이터도 도메인과 무관한 공개셋(COCO keypoint, 영상 분류
벤치마크)일 수밖에 없고, 그러면 06과 같은 실패 패턴(기법에 데이터를
강제로 맞춤)이 반복된다. **02~08 문서 목록에서 제외** — 각 md 상단에 배너로
표시했다. 하드웨어만 보면 둘 다 기술적으로는 가능하지만(08은 그마저도 문서
스스로 "최난도"라 적어뒀고 상시 VRAM 점유 서비스와 겹쳐 위험), 용도가 없는
이상 하드웨어 가능 여부는 판단에 영향을 주지 않는다.

**02·05 보류(제외 아님)**: 용도가 "위험"(02)이거나 "불확실"(05)이라 지금
당장 착수 근거는 약하지만, 04·08과 달리 완전히 상상 불가능한 영역은 아니다
(예: 05는 `assistants` 페르소나 아바타 생성 등). 제품 결정이 서면 재검토.

**03 재정의 검토**: gildle에 결빙구역(HazardZone)이 이미 있어 "도로 이미지를
분할해 결빙을 라우팅 가중치로" 쓸 수 있는지 별도로 검토했다 — 결론과 근거는
`03_semantic_segmentation_agent.md` §5 참고. 요약: **결빙 자체는 세그멘테이션
데이터셋(Cityscapes/Mapillary)에 클래스가 없어 기각**, 구조적 보도/차도
분할은 이미지 수집 경로가 미확정이라 **보류**.

**06(Sentinel)**: 이미 §5~§6에서 자체적으로 기법→용도 순서의 실패를 겪고
CLIP 분류/Laplacian variance로 방향 전환 완료 — 이 감사의 계기가 된 사례라
표에는 참고용으로만 표시.
