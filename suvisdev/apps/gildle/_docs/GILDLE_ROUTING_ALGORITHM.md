## 1. 경로 탐색을 직접 구현하기

### 1.1 왜 networkx를 걷어낼 이유가 생기는가

`nx.shortest_path`는 **단일 기준 다익스트라**다. 아래 세 가지는 이 API로 표현이 안 된다.

| 요구 | networkx 한 번 호출로 되나 |
|---|---|
| 시간에 따라 바뀌는 그늘(걷는 동안 슬롯이 넘어감) | ✗ 슬롯 하나로 고정 |
| "거리 ≤ 1.3×최단" 같은 **제약** 아래 그늘 최대화 | ✗ 가중합만 가능 |
| 산책용 **루프 경로**(출발=도착, 목표 거리 D) | ✗ 최단경로는 항상 0m |

세 번째가 핵심이다 — 산책 앱인데 최단경로 엔진은 "집에서 집"을 못 만든다.

### 1.2 단계별 구현 (각각 독립 PR 크기)

포트 `RouteGraphPort.find_shortest_path(graph, start, end, weight_fn)`은 그대로 두고
어댑터만 갈아 끼우면 유스케이스·라우터·테스트가 안 바뀐다.

#### ① 자체 다익스트라 (`HeapDijkstraRouteGraphAdapter`)

```
dist[start]=0; heap=[(0,start)]
while heap:
    d,u = pop
    if u==end: break
    if d>dist[u]: continue           # 지연 삭제
    for v,edge in adj[u]:
        nd = d + weight_fn(edge)      # 방문한 간선만 평가 — 현재 설계와 동일
        if nd < dist[v]: dist[v]=nd; prev[v]=u; push(nd,v)
경로 = prev를 end에서 거꾸로
```
- 인접 리스트 `dict[str, list[(str, RouteEdge)]]`를 `build_graph`에서 만든다
  (현재 `_graph_cache`처럼 edges 리스트 동일성으로 캐시).
- **검증**: 23만 간선 실데이터에서 임의 (start,end) 200쌍의 경로 비용이 networkx와
  동일(부동소수 오차 1e-6)해야 한다. 하네스 §3-②.

#### ② A\* — 하버사인 휴리스틱

- `h(v) = distance_to(end)` (미터). 모든 간선 가중치 ≥ 거리(감면 모드 제외)이면
  admissible. **봄가을 ×0.7 감면 때문에 h를 0.7배**로 줘야 최적성이 유지된다 —
  모드별 최소 배율을 `RouteWeightCalculator.min_multiplier(mode)`로 노출.
- 효과: 서울 전역 그래프에서 방문 노드 수 5~20배 감소(직선 방향으로만 확장).
- **검증**: ①과 경로 비용 동일 + 방문 노드 수 < ①의 30%.

#### ③ 시간 의존 그늘 (time-dependent shortest path)

- 도보 속도 v=1.2m/s 가정. 노드 도착 시각 t(u)=출발+dist_m(u)/v. 간선 (u,v)의 그늘은
  **t(u)가 속한 슬롯**의 값을 쓴다 → `weight_fn(edge, t)`로 시그니처 확장.
- FIFO 성질(늦게 출발하면 늦게 도착)이 성립하므로 다익스트라가 그대로 최적.
- 지금은 30분 산책이면 슬롯 하나로 퉁치지만, 60분이면 두 슬롯을 지나가며 오후엔
  그늘이 반대편으로 옮겨간다(하네스 케이스 2 실측: 09시 0.93 → 15시 0.06).

#### ④ 제약 최단경로 — "너무 돌지 않는 그늘길"

- 지금은 `×5` 페널티라서 그늘을 위해 **길이 5배까지** 돌 수 있다(하네스 케이스 3은
  600m로 잡혔지만 실데이터에선 한계 없음).
- 라그랑주 완화: 비용 = 거리 + λ·햇빛거리, λ를 이분탐색해 "거리 ≤ (1+ε)·최단"을
  만족하는 최대 λ를 찾는다(ε=0.3 기본). 다익스트라 6~8회.
- 대안(더 단순): 상위 K개 경로(Yen) 중 제약 만족·그늘 최대 선택.

#### ⑤ 루프 경로 — 산책의 본질

목표 거리 D, 출발점 s. 최단경로 엔진으로 **좋은 루프**를 만드는 표준 기법:

```
for 방위각 θ in 0..360 step 30:
    m1 = s에서 θ 방향 D/3 지점의 최근접 노드
    m2 = s에서 θ+60 방향 D/3 지점의 최근접 노드
    loop = path(s→m1) + path(m1→m2) + path(m2→s)      # 세 변, 가중치는 모드 규칙
    후보에 (|len(loop)−D|, 간선 중복률, 그늘비율) 기록
경로 겹침(왔던 길 되돌아감) 페널티 → 최선 1개 + 대안 2개 반환
```
- 왕복 중복을 막는 트릭: 2·3번째 탐색에서 이미 쓴 간선 가중치 ×3.
- 이게 있어야 `walks`(오늘 만든 기록 API)가 "추천 루프 vs 실제 걸은 루프"를 비교할 수
  있다 — §2의 학습 데이터가 여기서 나온다.

#### ⑥ 다기준(Pareto) — 선택 사항

거리·그늘·가로수·위험을 가중합하지 않고 파레토 프론트를 구해 사용자에게 3안
제시. 라벨 세팅 다익스트라(각 노드에 비지배 라벨 집합). 간선 23만이면 실용적이나
구현 난도 높음. ④·⑤가 먼저다.

### 1.3 구현 현황 (2026-09-22 저녁)

①~⑤ 전부 구현했다. 포트 `RouteGraphPort`는 `find_shortest_path`를 그대로 두고
`find_shortest_path_time_dependent`(기본 구현은 시각 무시)만 더했으므로 networkx·PG
구현체와 기존 테스트가 그대로 돈다.

| 단계 | 위치 | 검증 |
|---|---|---|
| ①② | `adapter/outbound/graph/dijkstra_route_graph_adapter.py` (`DijkstraRouteGraphAdapter`·`AStarRouteGraphAdapter`) | 실데이터 200쌍 **불일치 0**, 무작위 격자 5종 동일 |
| ③ | `find_shortest_path_time_dependent` + `CalculateDogFriendlyRouteInteractor.execute_time_aware` | 출발 슬롯엔 직행이 그늘·200m 뒤엔 반대인 세계에서 경로가 도중에 옮겨감 |
| ④ | `execute_bounded` (t 이분탐색 8회) | 상한 0.3→직행 400m, 0.5→그늘 우회 600m, 7개 비율에서 상한 초과 0 |
| ⑤ | `app/use_cases/plan_loop_interactor.py` + `POST /gildle/loops` | 출발=도착·목표 ±35%·되밟기 ≤0.5, 여름엔 그늘 루프 우선 |

DI(`dependencies/route_provider.py`, csv 모드)는 `AStarRouteGraphAdapter`로 바꿨다.
`/navigate`는 `max_detour_ratio`를 주면 ④, 여름 낮이면 ③, 그 외엔 기존 경로다.

**정직한 실측**: 순수 Python 다익스트라는 networkx보다 느리다(200쌍 평균 0.39s vs
0.53s, A* 0.58s). A*의 방문 노드 감소도 13%뿐이다 — 여름 가중치가 거리의 1~5배라
휴리스틱 0.7×직선거리가 약하고, 서울 그래프는 격자가 아니라 방향 가지치기가 덜 먹는다.
교체의 근거는 속도가 아니라 **③④⑤가 networkx API로는 표현이 안 된다**는 것이다.

**모드별 휴리스틱 배율(2026-09-27 구현)**: `RouteWeightCalculator.min_multiplier(mode)`
(봄가을 0.7 · 여름·겨울 1.0)를 유스케이스가 `find_shortest_path(..., heuristic_scale=)`로 넘긴다.
"가중치 ≥ 거리 × 배율"이 모드마다 성립하므로 admissible. 실데이터 60쌍(`verify_routing_equivalence.py`,
수관 보강 후 데이터), 방문 노드 비율(다익스트라=1):

| 모드 | 배율 | 0.7 고정 | 모드 배율 | 질의당(다익/모드) |
|---|---|---|---|---|
| 봄가을 | 0.7 | 0.415 | 0.415 | 0.29s / 0.16s |
| 겨울 | 1.0 | 0.415 | **0.191** | 0.27s / **0.07s** |
| 여름 | 1.0 | 0.787 | **0.696** | 0.39s / 0.34s |

겨울은 대부분 간선이 거리 그대로라 직선거리가 거의 정확한 하한이고, 여름은 햇빛 ×5 때문에
여전히 느슨하다. 다음 수단은 노드 id 정수화, 그 다음이 랜드마크(ALT) 휴리스틱이다.

### ③을 가장 먼저 해야 하는 이유

①은 "코드가 규칙대로 움직인다"를 보장하지, "그림자가 실제와 맞다"를 보장하지 않는다.

5곳 사진이면 오차의 방향(과대/과소)이 나온다. 그 뒤에야 §2-C가 의미를 갖는다.
