## 결제 · PCI 규칙

> **현재 이 저장소에는 결제 코드가 없다** (2026-07-29 확인 — `payments`/`billing`
> 모듈, 카드·PSP 연동, 결제 관련 의존성 전부 부재). 따라서 지금 지켜야 할 PCI 항목도
> 없다. 이 파일은 **결제 기능이 실제로 들어올 때 발동하는 게이트**이며, 위 `paths`에
> 해당하는 파일이 생기는 순간부터 적용된다.
>
> 이 저장소가 PCI 심사를 통과했다는 뜻이 아니다. 아래는 "카드 데이터를 직접 다루지
> 않는 구조로 시작하라"는 최소 기준이지, 컴플라이언스 체크리스트의 대체물이 아니다.

### 1. 착수 전 확인

결제 코드를 처음 추가할 때는 **구현부터 하지 말고** 다음을 먼저 정한다.

- 결제대행사(PSP)를 무엇으로 쓰는가 — 국내면 토스페이먼츠·포트원 등.
- 카드 정보가 **우리 서버를 통과하는가**. 통과하지 않는 방식(PSP 위젯·리다이렉트로
  카드 입력을 위임하고 우리는 토큰만 받는 구조)을 기본으로 한다.
- 이 결정이 끝나기 전에는 스키마·엔티티를 만들지 않는다.

### 2. 카드 데이터 취급 (절대 규칙)

- **PAN(카드번호 전체)·CVV·유효기간·마그네틱 트랙 데이터를 저장하지 않는다.**
  DB 컬럼, 파일, 캐시(Redis) 어디에도 두지 않는다. CVV는 승인 직후에도 보관 금지다.
- 저장이 허용되는 것은 PSP가 준 **결제 토큰·거래 ID**, 그리고 표시용 마스킹 값
  (`**** **** **** 1234`, 카드사명) 뿐이다.
- **로그·에러 메시지에 결제 요청 본문을 그대로 남기지 않는다.** 이 저장소는 이미
  `lib/user-facing-error.ts`의 `safeApiErrorMessage`로 원시 payload를 UI에 노출하지
  않는 관례가 있다 — 결제 경로에도 같은 원칙을 적용하고, 서버 로그도 마스킹한다.
- 프론트에서 카드 정보를 `useState`·`localStorage`·URL 쿼리에 담지 않는다.

### 3. 통신·시크릿

- 결제 관련 통신은 예외 없이 HTTPS. 로컬 개발이라도 PSP 테스트 키를 평문 HTTP로
  보내지 않는다.
- PSP 시크릿 키는 **서버 전용**이다. `NEXT_PUBLIC_` 접두사를 붙이지 않고,
  `app/api/**/route.ts` 또는 백엔드에서만 읽는다(`.claude/rules/api-standards.md` §1).
- 키는 `suvisdev/.env`에 두고 커밋하지 않는다. 클라이언트 키와 시크릿 키를 혼동하지
  않는다.

### 4. 서버 측 검증

- **결제 금액을 클라이언트가 보낸 값으로 신뢰하지 않는다.** 주문 ID로 서버에서
  금액을 다시 계산해 PSP 승인 금액과 대조한다.
- PSP 웹훅은 서명을 검증한다. 검증 없이 상태를 바꾸지 않는다.
- 결제 상태 변경 엔드포인트는 소유권을 확인한다 — `pick_id`만으로 갱신하던
  `market_picks_router.py`의 IDOR 패턴을 반복하지 않는다.

### 5. 이 파일 갱신

결제 기능이 실제로 들어오면 위 "현재 결제 코드가 없다"는 배너를 지우고, 채택한
PSP·연동 방식·카드 데이터 흐름을 여기에 적는다. 그 전까지 이 파일의 내용을 "이미
적용된 규칙"으로 인용하지 않는다.
